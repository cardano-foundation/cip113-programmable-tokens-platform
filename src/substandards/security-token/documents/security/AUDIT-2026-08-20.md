## 1. Medium findings

### M-1 Blueprint compiled by a different Aiken than the one pinned (deployment / reproducibility)

**Location** `plutus.json:7-10` (`"version": "v1.1.23+8949565"`), `aiken.toml:3`
(`compiler = "v1.1.22"`), `.github/workflows/tests.yml:15-17` (installs v1.1.22), `README.md:139`.
The vendored `anastasia-labs/aiken-design-patterns` itself declares `compiler = "v1.1.23"`, and
`aiken.toml:28-30` explains a v1.1.23-specific resolution quirk — the toolchain actually in use is
v1.1.23.

**Why it matters** Aiken's `compiler` field is descriptive, not enforced. Patch releases can change
UPLC output for identical source; if they do, a CI build (v1.1.22) and the committed blueprint
(v1.1.23) yield different script hashes, policy ids and addresses. Whoever derives genesis
parameters from the "wrong" one deploys a protocol whose registry entries and GlobalState address
do not match the scripts the off-chain tooling later references. Fails closed/inert, but only
discovered at genesis.

**Fix** Pick one toolchain and make it enforceable: bump `aiken.toml` and CI to v1.1.23 (matches
the blueprint and the dependency) **or** rebuild with a genuine v1.1.22 and commit that blueprint.
Either way add a reproducibility gate to CI: `aiken build && git diff --exit-code plutus.json`.

**Location** `README.md:148-184`. Verified against `plutus.json` parameter titles (which match the
source declarations exactly — §5.4) and the validator declarations. Per validator, parameters the
README never names:

|---|---|---|
| `power_users_validator` (spend) | `global_state_policy_id, power_users_linked_list_policy_id` | `global_state_policy_id` |
| `global_state_spend_validator` | `security_asset_name, issuance_policy_id, global_state_policy_id, power_user_list_script_hash` | `security_asset_name`, `global_state_policy_id` |

| `third_party_transfer_logic_validator` | `security_asset_name, power_users_linked_list_policy_id, global_state_policy_id, registry_policy_id, expected_issuance_policy_id, denylist_script_hash, power_user_list_script_hash, plb_script_hash` | 4 of 8; conflates the power-users *script hash* with the separately required *policy id* |
| `minting_authority_validator` | `security_asset_name, global_state_policy_id, registry_policy_id, power_users_linked_list_policy_id, minting_logic_script_credential_hash, expected_issuance_policy_id, plb_script_hash, denylist_script_hash, power_user_list_script_hash, reference_asset_name` | 6 of 10; `registry_policy_id` and `reference_asset_name` appear nowhere in the README |

Also: `registry_policy_id` and `plb_script_hash` are CIP-113 base-layer constants this repo
consumes but does not produce; the README never says where to obtain them (prerequisite before
step 1). And `minting_authority_validator`'s `minting_logic_script_credential_hash` and
`expected_issuance_policy_id` must be supplied with the **identical** 28-byte value (the proxy's
hash *is* the issuance policy id) — two separately named slots for one value is a deploy-script
footgun worth an assertion.

**Why it matters** There is no off-chain deploy script in the repo; the README is the only
parameter-application guidance. `aiken blueprint apply` is positional: under-supplying or
mis-ordering either errors or silently produces a validator hash no real transaction can satisfy
(fails closed, but at genesis).

**Fix** Replace the prose of step 6 (and patch steps 2 and 5) with the table above, add the two
external constants as prerequisites, note the identical-value pair, and add the reference-script
note (I-4). Or state that the section explains provenance only and point at the blueprint's titled
parameter arrays as authoritative.

### M-3 No positive KYC-proof test anywhere (test coverage, one-directional)

**Location** `lib/kyc/verify.ak:474-958` — all 22 tests that exercise
`verify_attestation_proof` / `verify_membership_proof` / `verify_kyc_proof` are `!verify_…`.
The two positive-shaped tests (803, 824) only cover the leaf encoders. No test in the repo
constructs a genuine Ed25519 signature or a non-trivial MPF root; the only validator-level test
that passes with a proof does so because `requires_receiver_kyc=False`
(`minting_authority.ak:1233-1243, 1667-1675`).

**Why it matters** A regression that makes the verifier permanently return False is invisible to
the suite and surfaces in production as every KYC-gated transfer/mint/seizure failing —
indistinguishable on-chain from a deliberate freeze. (The mirror regression — always True — *would*
be caught.)

**Fix** One positive test per proof type with a hard-coded keypair/signature and a hard-coded
single-leaf MPF root + proof, plus one end-to-end `run_transfer` / `run_withdraw` success with
`requires_*_kyc = True`.

### M-4 Seven of thirteen GlobalState spend branches are untested (test coverage)

**Location** `validators/global_state.ak:319-465` — `ModifySecurityInfo`, `AddTrustedEntity`,
`RemoveTrustedEntity`, `UpdateTrustedEntity`, `SetRequiresSenderKyc`, `SetRequiresReceiverKyc`,
`UpdateMemberRootHash` have no positive control and no negative test of their admin-signature,
precondition or anti-smuggling guards. `deactivated_input_rejects_modify_security_info` (1011)
traps on the top-level guard (215) before reaching the branch. `gs_setters_round_trip`
(`lib/types/global_state.ak:624-671`) covers `set_requires_receiver_kyc` but not its sibling
`set_requires_sender_kyc`.

**Why it matters** `trusted_entity_vkeys` is the entire KYC issuer trust root
(`lib/kyc/verify.ak:109`); its only writers are untested. A transposition between
`idx_requires_sender_kyc` / `idx_requires_receiver_kyc` would go unnoticed.

**Fix** Per branch: positive admin-signed test, missing-signature test, precondition test
(duplicate vkey, missing vkey, bad root length…), smuggling test — the existing `rotate_admin_*`
pattern. Add `set_requires_sender_kyc` to the round-trip test.

## 2. Low findings

### L-1 List spend validators let a co-located non-list UTxO be swept alongside any genuine mutation (vulnerability, privileged actor)

`validators/denylist.ak:58`, `validators/power_users.ak:21-33` delegate the spend to the library's
`spend_for_adding_or_removing_an_element`, whose body is "some token of this policy is minted or
burned in this tx" — it takes no input/datum argument. Our `count_inputs_with_policy` only counts
inputs that *carry* the list policy. So a stray UTxO at the list address (any value, no datum) can
be added as a third input to an admin's `RemoveFromDenylist` and its value routed to change. No list
state is corrupted, the actor is already privileged, the list address is not a deposit target —
hence Low. **Fix** in both spend handlers: `expect Some(spent) = find_input(self.inputs,
own_ref)` and require `quantity_of_policy_id(spent.output.value, list_policy) > 0` before
delegating.

### L-2 Zero-amount mint / registration requires `can_burn`, not `can_mint` (liveness)

`validators/minting_authority.ak:697` — `if minted_amount > 0 { can_mint } else { can_burn }`.
A `RegisterMint` that mints only the CIP-68 reference NFT (initial supply 0) or a no-op `MintBurn`
is rejected for a `can_mint`-only operator; both branches share `verify_mint_or_burn` (285-298), so
the quirk is reachable at first registration too. Reachable (`only_permitted_assets_minted`
allows it, `RegisterStructural` forbids minting the reference NFT at all). Workaround: mint ≥1 unit
to the operator's own credential. **Fix** `if minted_amount >= 0 { can_mint } else { can_burn }`.

### L-3 GlobalState datum growth is unbounded (liveness, admin-only)

`validators/global_state.ak:319-357`, `lib/types/global_state.ak:10-11` —
`ModifySecurityInfo.new_security_info` and `TrustedEntityMetadata` are raw `Data`, and nothing
caps `list.length(trusted_entity_vkeys)`. The first-pass claim of an irreversible execution-budget
brick was **downgraded**: `maxTxSize` (16 KiB) bounds any single write, `unconstr_fields` is
O(fields), and the setters splice only the new value so shrinking is always cheap. The residual is
a self-limiting headroom squeeze. **Fix (defence-in-depth)** cap
`bytearray.length(builtin.serialise_data(…))` of the two `Data` fields and the entity-list length
at genesis and on every mutation.

### L-4 Transfer-path execution budget at large party counts is still unmeasured (liveness)

`lib/compliance.ak:41-98` recurses once per unique party with no cap; per party it runs a denylist
absence proof (~31.8M CPU measured after the v1.8.0 upgrade, `security-fixes.md:71-74`) and, when
KYC is on, one Ed25519 verification. Both validators call it twice (senders, destinations). Rough
static ceiling from the absence proof alone ≈300 parties against the 10 G-step limit, shared with
the base-layer scripts; redeemer size (≈163 B per attestation) probably binds first at ~40-50
parties. **Downgraded** from Medium because nothing was measured (Bash denied) and the project
already lists it as open. **Action** add an N-party fixture to `regression.ak` and read the
`[mem, cpu]` the runner prints for N = 1, 4, 16, 32; document a safe max and chunk bulk operations
off-chain. No on-chain cap is recommended.

### L-5 Sender fold does not pin the PLB payment credential (defence-in-depth)

`validators/transfer_logic_script.ak:113-130` extracts the stake credential of every input
carrying the security asset without asserting `payment_credential == Script(plb_script_hash)`;
the destination fold (144-153) does, with a comment explaining why. Unreachable today (base-layer
`no_escape` + per-policy conservation keep every such UTxO in the PLB), so Low. **Fix** mirror
lines 152-153 in the sender fold.

### L-6 `ModifyPowerUser` and `power_users` `Init`/`Deinit` have no tests

`validators/power_users.ak:34-74, 89-141` — the only in-place rewriter of
`is_admin/can_mint/can_burn/can_pause/can_force_transfer` has no positive or negative test; the
admin gate (46) and the `wanted_user_state == parsed output` binding (55-65) are correct as read.
Downgraded from Medium for that reason. **Fix** mirror `denylist_init_*`/`denylist_deinit_*` and add
positive / missing-signature / disagreeing-datum tests.

### L-7 `global_state_mint_validator` is never invoked by a test

`validators/global_state.ak:124-158` — only `sanitise_initial_datum` is unit-tested; the one-shot
nonce, output-locating and `quantity_of_policy_id == 1` shape guard have no validator-level test,
although `regression.ak` already shows the pattern for the two list mint validators. **Fix** a
`run_mint` wrapper plus positive / missing-nonce / extra-asset-name / quantity-2 / no-output tests.

### L-8 Four `sanitise_initial_datum` conjuncts lack a negative test

`validators/global_state.ak:70-75` — `mintable_amount >= 0`, 28-byte `admin_credential_hash`,
28-byte `minting_script_credential_hash`, born-paused / born-deactivated. A malformed
`admin_credential_hash` or negative `mintable_amount` at genesis is *not* correctable later
(`RotateAdmin` is gated by the very hash; `remaining_amount >= 0` can never recover);
`minting_script_credential_hash` is (admin-gated rotation). **Fix** five `sanitise_rejects_*` tests.

### L-9 Denylist covering node re-authenticated once per party (optimization)

`lib/compliance.ak:77-83`, `lib/denylist/absence.ak:48-91` — several parties citing the same
`covering_ref_input_index` re-run `get_element_info`/`run_element_with` each time. Only worth an
accumulator if L-4's benchmark shows it matters.

### L-10 `UpgradeRegistryNode` does not sanity-check the credential *type* of the new logic fields (operator footgun)

`validators/minting_authority.ak:366-378` re-asserts only fields 5/6; an admin-signed upgrade can
set field 3/4 to a `VerificationKey`, after which every ordinary transfer (or seizure) fails until
another upgrade — irrecoverable only if `LockUpgrades` follows. Same class as the documented
`minting_script_credential_hash` footgun. **Fix** `expect Script(_) = …` on both new fields, or at
least the runbook note. (Single-lens; not adversarially re-verified.)

### L-11 `UpgradeRegistryNode` has no local backstop that the registry node's `next` pointer is preserved (defence-in-depth; second pass)

`validators/minting_authority.ak:301-401` re-derives and pins `key` and `minting_logic_script`
(345) and re-asserts `unfracking_logic_script` / `global_state_cs` (366-378), but never reads
field 1 (`next`) of either the spent or the continuing node. The code comment
(`lib/types/minting_authority.ak:74-93`) relies on the base layer's `registry_spend` update path to
freeze `key`/`next`/`minting_logic_script`; the 2026-08-19 base-layer verification confirmed the
*insert*-time ordering, not the update path specifically. If that guarantee were ever weaker than
documented, this token's admin could corrupt a node inside the *shared* CIP-113 registry. Same
shape as the previous audit's defect 4 (a guarantee leaned on without a local backstop). **Fix**
two lines next to 366-378: `expect list.at(out_fields, 1) == list.at(spent_fields, 1)`. Also
re-check `registry_spend`'s update branch in `cardano-foundation/cip113-programmable-tokens` the
way A-1/A-2 were checked.

### L-12 List element keys are not length-checked to 28 bytes (hygiene; second pass)

`validators/denylist.ak:127-257` (`AddToDenylist.user_pkh`, `RemoveFromDenylist`),
`validators/power_users.ak:142-259` (`AddPowerUser.new_power_user_key`, `RemovePowerUser`) — none
asserts `bytearray.length(..) == 28`, unlike `RotateAdmin` (`global_state.ak:476`) and
`AddTrustedEntity` (353). Walked the obvious worry (a short key shadowing a real 28-byte target in
`covers_key`): it does **not** materialise — `bytearray.compare` is a strict total order for
unequal lengths, sortedness and the `remove` chain-integrity check hold, and presence equality is
byte-exact — so a fat-fingered short key only wastes a min-ADA deposit and clutters the list.
**Fix** length assertions on all four redeemer key fields.

## 4. What held — load-bearing defences (regression reference)

Every attack below was attempted by at least one agent and refuted by the cited line; most are
also pinned by a named test. Keep these lines when refactoring.

**GlobalState**
* Datum hijack → `address_preserved` compares the *full* address (`global_state.ak:231`).
* Field smuggling / extra fields → input typed as `GlobalStateDatum` before `unconstr_fields`
  (193-228), one `set_*` per branch emitting exactly 14 fields, `equals_data` on the whole datum,
  `InlineDatum` required (221); pinned by `*_cannot_smuggle_another_field_change`.
* Acting on a deactivated state → `expect !input_datum.deactivated` before dispatch (215).
* Second GlobalState NFT → one-shot `OutputReference` + `quantity_of_policy_id == 1` (126-146).
* Under-decrementing the cap → `minted_amount` read from `self.mint`, `remaining_amount >= 0`
  (271-289); any non-`MintSecurity` branch with a nonzero security mint fails
  `no_concurrent_security_mint` (258-262, all eleven branches).
* Pause/unpause by `can_pause` is by design (`lib/types/power_users.ak:20-21`); deactivate reads
  `transfers_paused` off the spent UTxO (536) — no ordering race.
* Moving a power-user node to a wallet to pause → address pin in `authenticated_power_user`
  (`utils.ak:129-130`); tests `pause_fails_when_the_power_user_node_is_*`.
* `RotateAdmin` 28-byte + dual signature (476-481); `AddTrustedEntity` 32-byte vkey, duplicate
  rejected, sorted insert (353-354); `UpdateMemberRootHash` 0-or-32 bytes (458-461).

**Minting proxy + authority**
* Forged GlobalState → `gs_datum_from_output` requires the NFT (`minting_logic_script.ak:55-58`).
* Bare signature instead of the authority running → `must_run_script_withdrawal` (76).
* Proxy naming itself as authority → `!= own_hash` (68).
* GS as reference-only for a mint → `MintBurn`/`RegisterMint` resolve GS via `self.inputs`
  (625, 239); `UpgradeRegistryNode`/`RegisterStructural` use reference inputs but require an empty
  issuance-policy mint (395, 430).
* Role/sign mismatch → role gate keyed on ledger `minted_amount` (690-701).
* Third asset name / netting games → per-name walk in `only_permitted_assets_minted` (463-491),
  `dict.is_empty` shape checks (395, 430); reference NFT untouchable outside `RegisterMint`
  (200-206, 480-486) and pinned by `reference_nft_output_is_pinned` (508-529).
* Burn-plus-redistribute → any burn spends a PLB UTxO, forcing the base layer to run the transfer
  logic, which vets every input and output; the authority needs no destination check on burns.
* Escape to a non-PLB output → `verify_mint_destinations` (731-739).
* Self-mint KYC exemption → skips only the KYC arm; denylist absence still runs (787-793).
* Registry-node update riding on a mint → unconditional "no registry-policy input" in `MintBurn`
  (186-195).
* Decoy registration / decoy upgrade output → `verify_registration_structure` binds the *named*
  node's own NFT (570-574); `derive_issuance_policy_id_from_registry_node` needs a genuine NFT
  (335-345); foreign-keyed node → `== expected_issuance_policy_id` (182, 321, 345, 568).
* Front-running registration → key↔proxy binding + proxy withdraw-0 + admin signature (282/433).
